الملخص

يتلخص هذا المشروع في بناء تطبيق موبايل باسم Kiddy Link يهدف إلى ربط روضة أطفال واحدة بأولياء الأمور رقميًا، بما يسهّل متابعة الأطفال يوميًا ويعزّز التواصل بين البيت والروضة ضمن قناة رسمية وآمنة.

  • مديرة الروضة: إدارة الحسابات، الموافقات، التقويم، البانرات، الإشعارات، والملصقات.
  • المعلمة: الحضور، الوجبات، الصور، الواجبات، البث المباشر، والدردشة مع أولياء الأمور.
  • ولي الأمر: متابعة أطفاله ومشاهدة البث والدردشة مع المعلمة.

قاعدة البياناتMySQL / MariaDB
خدماتRedis، Storage، Agora، OpenAI

الإهداء

إلى الأهل الكرام، وإلى المشرف والأساتذة الأفاضل، وإلى كل من آمن بفكرة ربط البيت بالروضة رقميًا.

المقدمة

مع توسّع التطبيقات الذكية، أصبحت روضات الأطفال بحاجة إلى قناة تواصل رقمية موثوقة تربط الإدارة والمعلمات بأولياء الأمور، بعيدًا عن تشتت الرسائل عبر واتساب. من هنا جاءت فكرة Kiddy Link: تطبيق موبايل عربي بالكامل بواجهات حسب الدور، مع خادم مركزي للبيانات والصلاحيات والإشعارات والبث.

الفصل الأول: مرحلة الاستهلال

ملخص المشروع

Kiddy Link تطبيق موبايل يربط روضة واحدة بأولياء الأمور عبر ثلاث واجهات. الحسابات تُنشأ بواسطة المديرة فقط. تم بناء API ونشره وتشغيل تجربة APK.

الشكل 1.0 — المعمار العام لنظام Kiddy Link

نبذة عن النظام

Client–Server: Flutter ↔ NestJS عبر HTTPS/WS، MySQL للبيانات، Redis مساعد، تخزين ملفات، Agora للبث، OpenAI لتحليل الواجبات من الخادم فقط.

منهجية البحث (RUP)

الشكل 1.1 — مراحل منهجية RUP

  • Elaboration: المشكلة والمتطلبات والجدوى.
  • Construction: UML والبناء.
  • Transition: الاختبار والنشر.

أهداف المشروع

  • قناة رقمية موثوقة بين الروضة والبيت.
  • إدارة مركزية للصلاحيات والموافقات.
  • توثيق يومي للمعلمة ومتابعة لولي الأمر.
  • نشر API وإصدار APK للتجربة.

  • مقابلات مع مديرة/معلمة/ولي أمر.

  • مراجعة DEVELOPER_SPEC ومخطط Prisma.

توثيق حالات الاستخدام

1) توثيق حالة الاستخدام: تسجيل الدخول

  • الممثل الأساسي: جميع الأدوار
  • المتطلب السابق: وجود حساب منشأ من المديرة
  • خطوات العمل الرئيسية: فتح التطبيق ← إدخال البيانات ← POST /auth/login ← استلام التوكن ← التوجيه حسب الدور
  • المسار البديل: بيانات خاطئة أو حساب غير نشط ← رسالة خطأ عربية
  • العمليات اللاحقة: الدخول للواجهة الخاصة بالدور

2) توثيق حالة الاستخدام: إدارة الحسابات

  • الممثل الأساسي: المديرة
  • المتطلب السابق: تسجيل دخول المديرة
  • خطوات العمل الرئيسية: إنشاء/تعديل/تعطيل معلمة أو ولي أمر وربط الأطفال
  • المسار البديل: بيانات ناقصة أو اسم مستخدم مكرر
  • العمليات اللاحقة: ظهور الحساب في القوائم

3) توثيق حالة الاستخدام: الموافقة على الصور

  • الممثل الأساسي: المديرة
  • المتطلب السابق: صور بحالة pending
  • خطوات العمل الرئيسية: عرض الصور المعلقة ← موافقة/رفض ← تحديث الحالة
  • المسار البديل: رفض الصورة
  • العمليات اللاحقة: ظهور الصورة لولي الأمر مع إشعار

4) توثيق حالة الاستخدام: إدارة التقويم والبانرات

  • الممثل الأساسي: المديرة
  • المتطلب السابق: صلاحية مديرة
  • خطوات العمل الرئيسية: إضافة/تعديل أحداث وبانرات
  • المسار البديل: حقول غير مكتملة
  • العمليات اللاحقة: عرض المحتوى للمستخدمين

5) توثيق حالة الاستخدام: إدارة الملصقات والمستويات

  • الممثل الأساسي: المديرة
  • المتطلب السابق: صلاحية مديرة
  • خطوات العمل الرئيسية: إدارة sticker_levels والملصقات
  • المسار البديل: تعطيل مستوى مستخدم
  • العمليات اللاحقة: استخدام الملصقات في التحفيز

6) توثيق حالة الاستخدام: تسجيل الحضور

  • الممثل الأساسي: المعلمة
  • المتطلب السابق: معلمة مرتبطة بطلاب
  • خطوات العمل الرئيسية: اختيار الطالب ← check-in/out ← حفظ السجل
  • المسار البديل: طالب غير مرتبط
  • العمليات اللاحقة: تحديث ملخص ولي الأمر

7) توثيق حالة الاستخدام: تأكيد الوجبات

  • الممثل الأساسي: المعلمة / ولي الأمر
  • المتطلب السابق: سجل يومي للطفل
  • خطوات العمل الرئيسية: تأكيد الوجبة وحفظ MealRecord
  • المسار البديل: لا يوجد سجل
  • العمليات اللاحقة: تحديث حالة الوجبة

8) توثيق حالة الاستخدام: رفع صور الألبوم

  • الممثل الأساسي: المعلمة
  • المتطلب السابق: تسجيل دخول المعلمة
  • خطوات العمل الرئيسية: اختيار صورة ← رفع ← حالة pending
  • المسار البديل: نوع ملف غير مدعوم
  • العمليات اللاحقة: انتظار موافقة المديرة

9) توثيق حالة الاستخدام: الواجبات المنزلية

  • الممثل الأساسي: المعلمة / ولي الأمر
  • المتطلب السابق: طالب مرتبط
  • خطوات العمل الرئيسية: إنشاء واجب ← متابعة/رفع ← تقييم/AI
  • المسار البديل: ملف غير صالح
  • العمليات اللاحقة: حفظ الواجب والتقييم

10) توثيق حالة الاستخدام: بدء بث مباشر

  • الممثل الأساسي: المعلمة
  • المتطلب السابق: مفاتيح Agora مضبوطة
  • خطوات العمل الرئيسية: POST /live/start ← قناة وتوكن ← بدء البث
  • المسار البديل: بث نشط أو مفاتيح ناقصة
  • العمليات اللاحقة: إشعار أولياء الأمور

11) توثيق حالة الاستخدام: مشاهدة البث

  • الممثل الأساسي: ولي الأمر
  • المتطلب السابق: بث نشط لمعلمة الطفل
  • خطوات العمل الرئيسية: فتح البث ← join ← استلام توكن
  • المسار البديل: لا يوجد بث نشط
  • العمليات اللاحقة: عرض الفيديو

12) توثيق حالة الاستخدام: الدردشة

  • الممثل الأساسي: معلمة ↔ ولي أمر
  • المتطلب السابق: ارتباط بنفس الطفل
  • خطوات العمل الرئيسية: فتح محادثة ← إرسال نص/مرفق
  • المسار البديل: غير مصرح / شبكة
  • العمليات اللاحقة: حفظ الرسالة

13) توثيق حالة الاستخدام: متابعة الطفل

  • الممثل الأساسي: ولي أمر
  • المتطلب السابق: أطفال مرتبطون
  • خطوات العمل الرئيسية: عرض ملخص الحضور والصور والواجبات
  • المسار البديل: لا أطفال ← رسالة فارغة
  • العمليات اللاحقة: التنقل للتفاصيل

الاختبار

اختبار الدخول حسب الدور، الحسابات، الحضور، الوجبات، الصور والموافقة، الواجبات، الدردشة، والبث، مع حالات الخطأ والفراغ.

تطوير النظام

بناء NestJS/Prisma وFlutter، ثم إصلاح الملاحظات وربط الإنتاج (PM2 على 3010 + Apache Proxy).

الاختبار النهائي

  • وحدات → ترابط → تكامل → نظام كامل عبر APK الإنتاج.

النتائج

  • تطبيق عربي متعدد الأدوار.
  • API على https://kiddylink.baitpait.com/api.
  • متابعة يومية وتواصل وبث.
  • APK للتجربة.

المشاكل والتوصيات

  • تعقيد التكامل، حجم APK، استكمال FCM، WebSocket عبر Proxy.
  • توصيات: FCM، proxy_wstunnel، توقيع Release، اختبارات آلية، تقارير أغنى.
